# Magpie Runbook

Magpie v1 is an owner-only iOS 27 + CarPlay music app for your own Navidrome, with Lidarr for "Try this song". This page tells you how to run it against **your** servers. Details of what each milestone does are at the bottom (Reference).

Built so far: milestones M0 to M5 (sign in, browse, play, search, queue, lyrics, CarPlay library browsing, Lidarr connect, Try in "straight into your library" mode, Requests), M8 hardening (edge cases, security fixes, final-review fixes) and **M6 Finds mode** (a separate Finds folder, the Finds shelf, Keep and Not for me), which stays behind **Use a Finds folder** and is **off by default** (section 3a), and **M7 polish** (Character dial and Immersive-lite, the "Play now" landing banner, Bring in more after Keep, Made for you on Home, "Not in your library" albums on the Artist page, and Finds, Keep and "Try it next" in CarPlay). The `m8` tag means M0–M5 + M8; the `m6` tag adds M6 on top; the `m7` tag adds M7. Not built yet: see section 5.

## 1. Test on your own servers in 5 steps

**Step 1. Build and open it.** You need Xcode 27.1 at `/Applications/Xcode.app` and XcodeGen (`brew install xcodegen`).
```sh
cd /Users/dev/Dev/navidrome_player
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcodegen generate
open Magpie.xcodeproj
```
In Xcode pick the **Magpie** scheme and the **iPhone 18 Pro** simulator (iOS 27.0 runtime), then press Run. Or from Terminal: `scripts/build.sh`.
- Keep simulators apart: the one you sign in to your real servers with is for you only. The test scripts use their own simulator, **Magpie Tests** (section 6); never run tests on a simulator that is signed in to real servers.
- `xcode-select -p` currently points at the Command Line Tools, so bare `xcodebuild` and `simctl` fail. The scripts and the `export` line above work around it. To fix it for good: `sudo xcode-select -s /Applications/Xcode.app`. First run may also need `xcodebuild -runFirstLaunch` and accepting the license.

**Step 2. Connect to Navidrome.** The first screen asks for an address, user and password. Use an admin account if you want the pre-flight checks to be complete.
- Address: `https://music.example.com`, or `http://192.168.1.20:4533` / `http://myserver:4533` on your LAN, or a Tailscale name over `https://`. Several addresses are allowed (first one that answers wins). Include the base path if your proxy has one (`https://host/navidrome`).
- Typed without a scheme: it becomes `https://`, except private addresses (LAN, `.local`, single-word names, Tailscale 100.x), which become `http://`. A Tailscale MagicDNS name (`nas.tail1234.ts.net:4533`) becomes `https://`. **Debug builds in the simulator only:** Navidrome and Lidarr speak plain http on their own ports, so there you can type `http://` in front (Connect says so if https fails). TestFlight (Release) builds block plain http to `*.ts.net` names and Tailscale IPs (100.x) (Connect says so before trying): use the single-word name at home, or give the machine HTTPS (`tailscale serve` or `tailscale cert`) and use `https://` (docs/TESTFLIGHT.md step 9).
- Plain `http://` to a public-looking address: Connect warns "This address isn't encrypted. Your password will be sent in the clear." and asks you to agree. The answer is remembered per address. Prefer HTTPS for anything outside your house.
- Self-signed certificate: Magpie does not trust it (playback would ignore any override). Install your CA in the simulator, then reconnect:
  `xcrun simctl keychain booted add-root-cert /path/to/ca.pem`
- Do not put `user:password@` in the address; it is refused.

**Step 3. Browse and play.** Tap "Start listening". Open an album, play a track, try Search, the queue (from Now Playing) and lyrics. Nothing is written to your servers yet, except scrobbles (see warnings in section 3: switch **Count plays** off in Settings if you don't want test plays recorded).

**Step 4. Connect Lidarr (read-only first).** Home › "Finish setting up" › Connect Lidarr. Enter the address and API key (Lidarr › Settings › General). Magpie checks the key and shows a summary: version, root folders and free space, whether Tubifarry was found, recycle bin, and Lidarr's health messages. Nothing is written. Read it (and section 2).

**Step 5. Allow changes, set up, and Try one song.**
1. Library › gear › Lidarr: switch on **Allow Magpie to change Lidarr** (off by default; per Lidarr).
2. Tap **Set up Magpie in Lidarr**. It creates only what is missing (section 3).
3. Choose **New music goes to** (your root folder; Magpie never guesses if you have several).
4. Search for a song you do not own. In the "Not in your library" band tap **Try** (or **Ask for it** if you have no Tubifarry). Watch Library › Requests. Then check **Settings › Lidarr change log** and Lidarr's own Activity page.

Start with one song by a small artist, preferably one you wouldn't mind seeing in Lidarr.

## 2. Pre-flight checks before you Try

Check these once; none of them need Magpie.

| Check | How | If it fails |
|---|---|---|
| Navidrome 0.63.2 or newer, and an admin login | Navidrome footer / About page | 0.63.2 was verified on a real server (song paging, `/api/library`, targeted scans, lyrics); older versions are untested. A non-admin works for listening but can't scan the library |
| Lidarr 3.x reachable from the Mac | Connect Lidarr shows its version | v1 was verified on 3.2.0.5144 (develop channel). 3.1.x should work. See the monitor note in section 3 |
| Lidarr recycle bin set | Lidarr › Settings › Media Management › Recycle Bin (the Connect Lidarr summary shows "deletes are permanent" if unset) | Set one before you use **Not for me** (Finds mode): it deletes the find's files, and without a recycle bin they are gone for good. The confirm sheet then says "This deletes the files permanently." Magpie never changes this setting |
| Same music folder seen by both | Compare Lidarr's root folder path with Navidrome's library path | v1 has no path mapping. If they differ, a song never becomes **Ready** even though Lidarr imported it (Magpie checks that Navidrome lists it) |
| Subsonic connection works | Connect succeeded and Home shows shelves | Check the base path and that the address returns Subsonic JSON, not a login page |
| `songLyrics` extension | Lyrics button appears in Now Playing | Without it the lyrics sheet is hidden. Not a fault |
| Last.fm agent (top songs) | Artist screen shows "Popular" | Hidden when your server has none. Not a fault |
| Tubifarry | Connect Lidarr summary says found / not found | Found: speed **Standard** ("Try it", live wait screen). Not found: **Patient** ("Ask for it", shows up later in Requests) |

## 3. What Try does to your Lidarr, exactly

The whole write list, nothing else is ever sent:
- **Set up Magpie in Lidarr** creates, only if missing: quality profiles *Magpie Fast Start* and *Magpie Lossless*; metadata profiles *Magpie Finds* and *Magpie Albums+EPs*; tags `magpie` and `magpie-find`. If a profile with one of those names exists with different settings, set-up stops and tells you. Nothing you already have is edited.
- **Try, artist already in Lidarr:** Magpie picks the smallest release by that artist containing the song, sets just that one album to monitored (`PUT /album/monitor`) and starts an `AlbumSearch`. The artist, its profile and tags are not touched.
- **Try, new artist:** one `POST /artist` to your chosen root folder with *Magpie Fast Start*, metadata profile *Magpie Finds*, tag `magpie`, "monitor new items: none", only that release monitored, search on add.
- **The `addOptions.monitor` deviation:** the design said to send `addOptions.monitor: "none"`. On Lidarr 3.2.0.5144 that unmonitors the artist and searches zero albums, so Magpie leaves it out. Result: the artist stays monitored, new items are not monitored, and only the one album is. If your Lidarr is a different version, check the artist in Lidarr after your first Try that its monitored albums are only the one you asked for.
- **Searching:** if nothing is found, Magpie sends `AlbumSearch` again after 1 min, 5 min, 15 min, then hourly, giving up after 24 h (about 25 searches per request, at most 5 requests active at once). That is real load on your indexers.
- **Try and Stop looking never delete.** **Stop looking** unmonitors an album only if Magpie was the one who monitored it. An artist Magpie added stays in Lidarr; remove it there yourself if you want it gone. The only deletes Magpie ever sends are **Not for me** on a find (Finds mode, section 3a).
- **Finds mode (section 3a) adds:** **Keep** (`PUT /artist/editor`, moving a find's artist into your main root or only removing `magpie-find`, plus the restore writes when a move fails) and **Not for me** (deleting a find's release from the Finds folder). Both are spelled out in section 3a.
- **Bring in more** (after a Keep that moved the find, M7): `PUT /album/monitor` for the releases you pick, one `AlbumSearch`, and with Follow new releases `PUT /artist/editor {monitorNewItems: "new"}`. Exactly as in the M7 reference at the bottom.
- **Change log = undo map.** Every write (method, path, body, no secrets) is recorded on the phone before it is sent: Settings › Lidarr change log. Magpie also keeps an on-device ledger of albums it touched, per Lidarr (address + key).

**Warnings (B8, B9):**
- Try causes **real indexer searches and downloads** on your Lidarr and adds artists to your library root. Look at the change log afterwards.
- **Count plays** is on by default: plays are scrobbled by Navidrome to your ListenBrainz/Last.fm. Turn it off in Settings while testing if you don't want that.
- With **Use a Finds folder** off (the default) Try goes straight into your library, and the Try sheet says so. With it on, a new artist goes into your Finds folder instead (section 3a).

## 3a. Finds mode (M6): set-up, Keep and Not for me, exactly

Off by default. With it off nothing below happens, and finds already in the folder can still be kept or let go.

**Set it up** (Settings › Lidarr › Finds; needs Lidarr connected, **Set up Magpie in Lidarr** run, and an admin Navidrome login so the libraries can be read):
1. In Lidarr, add a root folder for finds (for example `/music/samples`) that is **not** inside, and does not hold, your main music folder or any other root folder. In Navidrome, add a library for the same folder.
2. Settings › Lidarr › Finds › **Finds folder**: pick that root folder and confirm "Use … for Finds? Magpie will only delete files it brought in here." Magpie never picks it for you, and refuses a folder that equals, holds or sits inside another root folder or the main root.
3. **In Navidrome**: pick the library that is the same folder. If Lidarr and Navidrome see it under different paths (different container mounts), give the two path starts under **Paths**.
4. Turn on **Use a Finds folder**. The footer says "Finds are set up." If it asks you to run set-up again, tap **Set up Magpie in Lidarr** (it adds the `magpie-find` tag).

**Try in Finds mode, new artist:** the same single `POST /artist` as section 3, but into the Finds root folder, tagged `magpie` **and** `magpie-find`. Before every add Magpie reads Lidarr's root folders again; if the Finds folder no longer checks out, the song goes into your main library and says so. An artist that is already in your Lidarr is handled exactly as in section 3 (one album monitored in place, never moved, tagged or deleted). The find shows up in Library › Finds when Navidrome lists it there; finds are never scrobbled.

**Keep** (a find's **Keep** button) writes, after checking on fresh Lidarr reads that the artist is one Magpie added (ledger), carries `magpie-find`, and sits strictly inside the Finds folder:
- normally one `PUT /artist/editor` with exactly `{artistIds:[id], rootFolderPath:<main root>, moveFiles:true, qualityProfileId:<Magpie Lossless>, tags:[<magpie-find>], applyTags:"remove"}`. Lidarr moves the whole artist folder into your main root folder in a `BulkMoveArtist` command; Magpie waits for it, then confirms the files are really in the new folder on disk (Lidarr's filesystem listing), scans both libraries and looks the song up again. The song shows "Lossless soon" until a lossless file replaces the MP3;
- if your main root already has a folder for that artist (or Lidarr's folder name differs at all from the find's), it moves nothing: `PUT /artist/editor {artistIds:[id], tags:[<magpie-find>], applyTags:"remove"}` only, and says "Kept. It'll stay in your Finds folder for now.";
- if the move fails, Magpie puts back what the PUT changed (`magpie-find` and the quality profile, and the root folder with `moveFiles:false` only when the files provably never left the Finds folder). What it can't settle within 30 minutes or 5 restore writes ends in **Needs attention**, and nothing more is written.

**Not for me** (swipe left on a find, long-press, or the VoiceOver action) deletes the find's **whole release** from your Finds folder. It is offered only on a ready find of an artist Magpie added in Finds mode: never on an artist that was already in your Lidarr, never for songs that went straight into your library. First a confirm sheet; it reads Lidarr's recycle bin and, when it is unset, says "This deletes the files permanently." Then, each step checked again on fresh Lidarr reads right before it is sent:
- refused (nothing written) unless: the ledger says Magpie added the artist and the album; nothing of the artist is kept, being kept, or needs attention; no other request is still bringing that album in; the Finds folder still checks out against Lidarr's root folders; the artist carries `magpie-find`; the artist folder and **every** track file of the artist are strictly inside the Finds folder and inside the artist's own folder (exact, case-sensitive comparison: `/music/samples-old` is not inside `/music/samples`); every file to delete is on disk exactly where Lidarr records it; no Lidarr move of the artist is running;
- `DELETE /api/v1/trackfile/bulk {trackFileIds:[…]}` for the album's files (on a Lidarr without that route, `DELETE /api/v1/trackfile/{id}` one at a time). Lidarr moves them to its recycle bin when one is set;
- `PUT /api/v1/album/monitor {albumIds:[id], monitored:false}`;
- `DELETE /api/v1/artist/{id}?deleteFiles=false&addImportListExclusion=false`, only if Magpie added the artist, no other request needs it, Lidarr records no track file and no other monitored album for it, and its folder holds **no file at all** on disk (Lidarr's filesystem listing, not its records). Otherwise the artist stays;
- the song leaves the queue (the one playing gives way to the next) and the Finds shelf, and Navidrome is asked to scan.
A lost answer is never followed by the same write until a fresh read shows what is still there. Writes and time are bounded (a few retries, 30 minutes); what can't be finished ends in **Needs attention** ("Couldn't finish letting it go · needs a look") and nothing more is written. Never sent, by any path: `deleteFiles=true`, `addImportListExclusion=true`, `DELETE /artist/editor`, `DELETE /api/missing`, or any change to your Lidarr settings.

**Lidarr 3.2 leaves track file paths stale after a move.** After Keep moves an artist (verified on 3.2.0.5144), `GET /trackfile` still reports the files at their old Finds-folder paths. Magpie therefore never trusts track file paths alone: Keep checks the moved files on disk with Lidarr's filesystem listing, and Not for me deletes a file only when the listing shows it exactly where Lidarr records it, inside the find's folder in the Finds root.

## 4. CarPlay in the simulator

**CarPlay was not visually verified overnight.** It is covered by unit tests of the templates and a clean-launch check, but nobody has watched it run, because the CarPlay window can't be driven from the command line. Please look at it.

1. Run Magpie in the iPhone 18 Pro simulator and sign in (Step 1 to 2).
2. Open **DeviceHub** (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`; older Xcodes: Simulator). Menu **I/O › External Displays › CarPlay**.
3. Tap Magpie on the CarPlay home screen. Check: four tabs (Home, Library, Finds, Search); Library › Albums › an album › a track plays and Now Playing shows the cover with Shuffle and Repeat; Search › "Type a search" opens the keyboard; after signing out, Home says "Not set up on this iPhone yet".
   - M7: with a Finds library chosen on the phone, the Finds tab lists New finds and Finds (round records, "New find" / "Find · n days left"); without one it says "Finds aren't set up on this iPhone". Play a find: Now Playing shows the add-to-library (+) button, which is Keep; a library song has none. Search a song you don't have (needs internet): its row says "Not in your library · Try · <artist>", and a tap opens "Try it next" / "Cancel". With an empty queue, Try it next starts songs from your library (the artist's first) and opens Now Playing; the find goes next in the queue when it's here.
4. Driving limits (only if your CarPlay window offers them): "Type a search" turns disabled ("Unavailable while driving") and long lists end with "Showing n of m".
- Device only: cold launch with a locked phone, and real head-unit artwork.
- CarPlay on a physical phone needs Apple's approved CarPlay audio entitlement in your provisioning profile; the simulator doesn't.

**On a real iPhone:** follow **docs/TESTFLIGHT.md** (TestFlight, or a free Personal Team run from Xcode). Device builds are CarPlay-less by default: they sign with `App/MagpieNoCarPlay.entitlements` (`MAGPIE_CARPLAY=NO`), so no approval is needed and the app simply doesn't appear in the car. Once Apple has granted CarPlay audio to your team, build with `MAGPIE_CARPLAY=YES` (`scripts/archive.sh --carplay`, or that build setting in Xcode). The simulator always carries the entitlement.
- First device launch after a reboot before unlocking (CarPlay cold start) waits for the unlock, then restores Navidrome and Lidarr.

## 5. Known limits, risks and troubleshooting

**Not built yet** (overnight order was hardening before features):
- Polish left after M7: the full Immersive look, Increase Contrast tokens, more themes, Siri and the assistant cell; in CarPlay, finds on their way and a Finds tab badge.
- Finds: no automatic expiry (days left is display only), no undo toast for Not for me (the recycle bin is the undo).
- Also missing: Up Next list and Downloaded in CarPlay, path mapping, Live Activity, mailbox/Listener/invites (v2).
- Some small review items were parked, not fixed (listed in the SDD ledger).

**Accepted security risks** (docs/reviews/security-v1.md):
- Debug builds allow `http://` to any address (their ATS dictionary has only `NSAllowsArbitraryLoads`: iOS ignores that key when `NSAllowsLocalNetworking` is also present, which is why Debug used to block http like Release); the in-app consent prompt is the protection, not the OS. Release (TestFlight) keeps only `NSAllowsLocalNetworking`: plain `http://` works with a single-word server name (`http://homeserver:4533`, verified for browsing and streaming) and, by Magpie's rules, LAN IPs and `.local`; a Tailscale IP (100.x) or `*.ts.net` name needs HTTPS. Connect and Connect Lidarr say so before trying: "This address needs HTTPS. At home you can also use your server's short name…"
- Plain `http://` to private/LAN addresses is not prompted; on a hostile network reusing your LAN range, an impostor server could get the password. Single-word host names (`music`, `nas`) count as home network.
- AVPlayer follows redirects itself, so the same-origin redirect rule covers browsing and artwork, not streams.
- Use HTTPS for anything that leaves your house. Plain http sends the password at sign-in, a replayable token on every stream URL and the Lidarr API key (full control of Lidarr).

**Navidrome login rate limit:** about 5 logins per 20 seconds, then **429**. If you reinstall and reconnect repeatedly, wait 20 s. Same for `scripts/it.sh` runs.

**Troubleshooting**
- LAN address times out but opens in Safari on the Mac: System Settings › Privacy & Security › Local Network, allow Xcode / Simulator. `localhost` in the simulator is the Mac.
- "Doesn't look like a music server": the address answered with a web page (router, captive portal, proxy login). Check the address and any proxy base path.
- Behind a reverse proxy at a sub-path, include the path in the address (`https://host/navidrome`, `https://host/lidarr`). If a proxy returns an HTML login page, Magpie shows an error instead of crashing; fix the proxy's auth (API paths must be reachable with the Subsonic/Lidarr credentials).
- Lidarr says wrong key: re-copy from Lidarr › Settings › General.
- Song stays "Bringing it home": see the path mapping row in section 2; after 20 minutes it says "Not showing up in your library yet" with **Check again**.
- Untrusted certificate: see Step 2.
- Disconnecting Lidarr, signing out, or connecting a different Lidarr turns the change switch off and forgets set-up; a new Lidarr always starts with changes off.
- **Signing out** also clears recent searches (phone and car) and the requests of **every** Lidarr this phone was connected to. It never deletes the Lidarr change log (your undo map), and it keeps the ListenBrainz token. The ledger (what Magpie may undo) is kept for every Lidarr that still has an unfinished entry, so a reconnected Lidarr is still handled safely; a Lidarr whose entries are all finished is forgotten.

## 6. Dev stack and tests

- **Dev stack** (throwaway local Navidrome + Lidarr with a fixture library, bound to 127.0.0.1): see `dev/README.md`. `dev/bootstrap.sh` starts and configures it, `dev/smoke.sh` checks every API the app uses. Needs Docker, curl, jq, openssl, ffmpeg. Tests only ever talk to localhost (a dev marker is required); never your real servers.
- `scripts/test-all.sh`: first `scripts/check-writes.sh` (G1: fails if product code, `Packages/MagpieKit/Sources` and `App/`, builds a POST/PUT/DELETE/PATCH request anywhere outside `LidarrKit/WriteGate.swift`, and if test code, `Packages/MagpieKit/Tests` and `Tests/`, sets a write method on a real request outside its short allowlist; Navidrome `auth/login` is the one allowlisted product write), then package tests (`swift test` in `Packages/MagpieKit`) then app unit and UI tests. `scripts/test-packages.sh` and `scripts/test-app.sh` run each half. `scripts/build.sh` builds only.
- **App tests run only on the "Magpie Tests" simulator** (iPhone 18 Pro, iOS 27.0). `scripts/test-app.sh` creates it when it is missing (`scripts/test-sim.sh`) and never touches any other simulator. Hosted unit tests launch the real app, and the UI tests reset its Keychain (`-MagpieResetState`), so **never run the test scripts against a simulator signed in to real servers**, and test against your real servers in a simulator of their own (the iPhone 18 Pro one in Step 1). As a test host the app also resumes no saved session and builds no request runner. Erasing "Magpie Tests" is always safe.
- `scripts/it.sh`: integration tests against the dev stack (`MAGPIE_IT=1`). `MAGPIE_IT=1 scripts/test-app.sh` adds the app flows. Wait about 20 s between runs (login rate limit).
- `Magpie.xcodeproj` and `App/Info.plist` are generated from `project.yml` (`xcodegen generate`) and are git-ignored.

# Reference: what each milestone does

## Details by milestone
- M7: polish, on the phone and in CarPlay.
  - **Appearance** (Task 7.1a): Settings › Appearance has the Character dial (cards drawn in their own looks; the app re-skins live) and accent swatches. Immersive-lite: a blurred, darkened cover behind Now Playing and Album, kept dark enough under text, with solid capsules (Reduce Transparency: no blur).
  - **Made for you** (Task 7.1c): with a ListenBrainz token, Home shows your newest created-for playlists (Daily Jams, Weekly Jams, Weekly Exploration). Songs you have play; the others are "Not in your library" rows with Try. No token: no shelf and nothing is asked. The token only ever goes to api.listenbrainz.org.
  - **Artist page, "Not in your library"** (Task 7.1c): with Lidarr connected, the artist's albums you don't have, newest first (read-only; editions such as "Deluxe" count as the album you have).
  - **CarPlay Finds** (Task 7.1d, D12): tabs Home · Library · Finds · Search (Finds is left out only if a car allows fewer than four tabs). The Finds tab is the phone's Finds shelf: New finds, then Finds with days left, as round records with a text status and symbol; tap plays. It follows the phone (a find played, kept or let go) and never reshapes while you look at it. Not for me isn't offered in the car.
  - **Keep in CarPlay** (Task 7.1d, D5): while a find that may be kept plays (the same finds the phone's Finds row offers Keep for), Now Playing shows the system add-to-library button. It runs the phone's Keep, for the find's release only (no Bring in more from the car), then shows as selected and says how it went ("Kept. It's in your library now.", "Kept. It'll stay in your Finds folder for now.", or why not). Now Playing always shows the real square cover.
  - **Try it next in CarPlay** (Task 7.1d, D6): the car's search now shows songs from outside your library after the library's (up to a third of a long list), as round records with "Not in your library · Try". A tap opens "Try it next" / "Cancel"; the sheet says what happens. Try it next runs the phone's Try. A find never interrupts something playing: when it's ready it goes next in your queue (the phone shows "Play now"). If the queue is empty, songs from your library start at once (the artist's first, topped up from random albums; never finds), so the find has something to follow and the app keeps running; if there's nothing to play first it says so, and the find starts when it's here (unless something else started meanwhile). A paused queue is kept: the find goes right after its song. Outside songs get 1.5 s in the car's search, so library rows never wait long. Patient ("Ask for it") songs are only asked for; they show up in Finds or your library when they're home. When Try isn't set up on the phone, the row only says "Not in your library".
  - Task 7.1b:
  - **Landing rule** (D6): a Try that becomes ready plays at once only while you are still on its wait screen (Try sheet or Requests) with the app open and nothing else playing. Otherwise it goes next in the queue (never cutting in) and the bottom bar shows "<song> is ready · Play now" (✕ dismisses). Patient ("Ask for it") requests don't land; they just show up. Several finds landing close together each go to the front of Up Next, so they play newest first (accepted for v1).
  - **Bring in more** (D5): after a Keep that moved the find into your library (not after "stays in your Finds folder for now" or a failed Keep), a sheet asks "Bring in more from <artist>?": Albums and EPs (preselected), This album only (the album the song is on, from MusicBrainz), Everything, plus **Follow new releases**. Each choice shows "about N hours of music" from the lengths Lidarr already knows, or no number. Writes (through the gate, logged): `PUT /album/monitor {albumIds, monitored: true}` for releases not monitored yet, one `AlbumSearch` for them, and with the toggle `PUT /artist/editor {artistIds: [id], monitorNewItems: "new"}` (the gate allows only that shape and only `new`, never `all` or `none`). Nothing is unmonitored, profiles and tags are untouched, albums another request is working on are skipped. Each release it brings in takes a place in the limit of five, like a song on its way, until Lidarr has its files, it is no longer monitored, or a day has passed. So one Bring in more brings in at most the places left (never more than 20, newest first), never more than the sheet showed. If fewer fit when you tap, it says how many wait. Following new releases downloads nothing now, so it works even when all five places are taken. Library's "on their way" and the "Five songs and releases are already on their way" message count both. Only for artists Magpie added. `scripts/it.sh` checks it in `FindsIT.keepMovesOnDevStack`.
- M6: Finds mode, behind **Use a Finds folder** (default off); see section 3a for set-up and the exact writes.
  - Set-up (Task 6.1): the owner confirms the Finds root folder (never guessed, never nested with another root), the Navidrome library that is the same folder, and a path mapping when the two see it under different paths. Path confinement (`PathGuard`) compares whole path components byte for byte.
  - Try into Finds (Task 6.2a): new artists go into the Finds root tagged `magpie` + `magpie-find`; Library › Finds shows New finds (here, not played yet), the other finds with days left (7 − days since they arrived; nothing leaves by itself), and finds on their way; the "Sample" hallmark; finds are never scrobbled.
  - Keep (Task 6.2b): moves the artist into the main root (or only untags it when the main root already has its folder), waits for Lidarr's move, proves the files on disk, scans both libraries and repoints the queue at the library song; "Lossless soon" until lossless.

## CarPlay simulator
Not automatable from the command line: the CarPlay window is a GUI menu item (UI scripting needs Accessibility permission for the terminal), and `simctl io` can't attach a CarPlay display. By hand:
1. `scripts/build.sh`, then run Magpie in the "iPhone 18 Pro" simulator (Xcode › Run, or `xcrun simctl install booted <DerivedData>/Build/Products/Debug-iphonesimulator/Magpie.app && xcrun simctl launch booted com.bleak-rooster.magpie`). Sign in (dev stack: `http://127.0.0.1:4533`, `NAVIDROME_ADMIN_*` from `dev/.env.local`).
2. In Xcode 27 the simulator window lives in **DeviceHub** (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`; older Xcodes: Simulator). Choose **I/O › External Displays › CarPlay**. Magpie appears on the CarPlay home screen; tap it.
3. Check: the four tabs (Finds included, M7; see section 4 step 3 for the Finds, Keep and Try it next checks); Library › Albums › an album › a track plays and Now Playing shows the cover with Shuffle and Repeat; the Search tab's "Type a search" opens the keyboard search; Home after signing out shows "Not set up on this iPhone yet".
4. Driving restrictions, where the CarPlay window offers them (limited keyboard / limited lists): the "Type a search" row turns disabled with "Unavailable while driving", and long lists end with "Showing n of m". Otherwise check this in a car.
- Entitlement: simulator builds carry `com.apple.developer.carplay-audio` in the simulated-entitlements section (`__TEXT,__entitlements`), not in the ad-hoc signature, so `codesign -d --entitlements -` shows an empty dict; that is expected. Check with `otool -X -s __TEXT __entitlements <Magpie.app>/Magpie` (hex of the plist) or the build's `Magpie.app-Simulated.xcent`. Putting the entitlement into the ad-hoc signature (`ENTITLEMENTS_DESTINATION=Signature`) makes the launch fail (`OS_REASON_EXEC`), so don't.
- Can't be tested in the simulator (device only): cold launch with the phone locked before first unlock; real head-unit artwork transparency.

## Connecting to a real server
- Self-signed HTTPS (B3): Magpie does not override certificate trust (AVPlayer would ignore it). Install your CA into the simulator with `xcrun simctl keychain booted add-root-cert <ca.pem>` (on a device, install and trust a profile). Connect says so when it sees an untrusted certificate.
- LAN address times out (B4) but opens in Safari on the Mac: check System Settings › Privacy & Security › Local Network for Xcode/Simulator. `localhost` in the simulator is the Mac.
- **Use HTTPS (a reverse proxy) for any address that leaves the house.** Plain `http://` sends the Navidrome password at sign-in, a replayable token on every stream URL and the Lidarr API key (full control of Lidarr) unencrypted.
- Plain HTTP outside the home network works only in Debug builds (B2); Release asks for HTTPS, also for Tailscale IPs and `*.ts.net` names (ATS doesn't count them as local; a single-word name works). Debug deliberately keeps `NSAllowsArbitraryLoads` (security review M2 ruling), and drops `NSAllowsLocalNetworking` so iOS honours it, so owner testing can use any `http://` address. The mitigation is in the app, not ATS: before the password or the Lidarr key goes over plain `http://` to an address that isn't loopback, LAN (10/8, 172.16/12, 192.168/16), link-local, `.local`, a single-label name, CGNAT/Tailscale (100.64/10) or IPv6 unique/link-local, Connect asks "This address isn't encrypted. Your password will be sent in the clear." The answer is remembered per address (scheme, host, port) in the app's settings.
- Addresses typed without `http://` or `https://` become `https://`, unless they are private (as above), which become `http://`. Addresses with `user:password@` are refused: enter credentials in their own fields.
- Before signing in, the address must answer `rest/ping` like a Subsonic server (`subsonic-response` with status ok, or failed with an authentication/missing-parameter error, which is how Navidrome answers a ping without credentials). A router, captive portal or proxy page that answers 200 gets nothing; Connect says the address "doesn't look like a music server".
- Redirects are followed only within the same scheme, host and port; a redirect elsewhere (or https to http) is refused and shows as an error.
- "Allow Magpie to change Lidarr" and the Lidarr set-up (profiles, tag, root folder) belong to one Lidarr (address + API key). Disconnecting Lidarr, signing out, or connecting another Lidarr turns the switch off and forgets the set-up; a newly connected Lidarr always starts with changes off.
