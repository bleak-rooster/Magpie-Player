## 2. Research (sources; "UNCONFIRMED" marks what only a device or the owner's server can show)

**Aurral 2.13.0 (github.com/lklynet/aurral, tag v2.13.0, read through the GitHub API).**
- `GET /api/playlists/status` (`playlistStatusSnapshot.ts`) returns, per flow and shared playlist: `id`, `ownerUserId`,
  `ownerUsername` (looked up from `userOps`), nothing about Navidrome. So Magpie already has the owner's identity for
  the Aurral side (`AurralFlow.ownerUserId/ownerUsername`, `isOwn(by:)`, D72(5)).
- **The Navidrome link exists server-side only.** `navidromePlaylistPointerStore.ts` keeps `{playlistId, title}` per
  flow/shared-playlist id in Aurral's settings table (key `navidromePlaylistPointers`). It is **not** in `/status`, and
  no allow-listed route returns it. (Whether Aurral's `/api/subsonic` façade, or `/api/settings`, exposes it is
  UNCONFIRMED; both are outside the allow-list and `/api/settings` is banned by D81, so don't use them.)
- docs `integrations/navidrome.mdx` ("Playlist names"): by default each Navidrome playlist is named
  **`username - playlist name`** (setting "Prefix playlist names with the owner username", can be turned off); a new
  playlist is public; **"The configured Navidrome account owns all Aurral playlists."** Consequences: (a) the Navidrome
  `owner` field is the same service account for every Aurral playlist, so it cannot tell users apart; (b) with the prefix
  on, the exact `<ownerUsername> - ` prefix IS an identity link (Aurral's own owner name); (c) with the prefix off two
  users' same-named flows give two same-named Navidrome playlists, which is the owner's bug.
- Deletes: `DELETE /api/playlists/flows/:flowId` (`flows.ts` 203) and `DELETE /api/playlists/shared-playlists/:playlistId`
  (`staticPlaylists.ts` 487). Both `requireFlowAccess`, answer 404 unless `getAccessibleFlow` / `getAccessibleStaticPlaylist`
  (the caller's own, or admin), and **queue** an operation (`delete-flow` / `shared-playlist-delete`) answering
  `{success, queued, operationId}` (200). A shared playlist's downloads shared with other playlists are kept
  (`getSharedDownloadReferences`); otherwise its pending work is cancelled. Operation status: `GET
  /shared-playlists/:id/operations/:operationId` (shared only; flows' operation read UNCONFIRMED).
- Jobs (`jobs.ts`): `POST /api/playlists/jobs/:jobId/approve` and `/deny` act only on a job with `status === "blocked"`
  (held for review). **Approve** imports the staged file. **Deny** discards the staging file, records the denied source
  (`recordDeniedSource`: that uploader/file or release is never picked again for this song) and sets the job `pending`
  again, so the worker searches another source: this is exactly "blocklist and re-search". `POST /jobs/:jobId/retry`
  (status in `RETRYABLE_JOB_STATUSES`; the set itself UNCONFIRMED) and `/jobs/:jobId/cancel` exist; `POST
  /research-missing` re-searches every accessible playlist (too broad, not wanted); manual source choice is
  `GET /jobs/:jobId/manual-search/sources`, `POST …/manual-search`, `…/select` (not this round).
  Whether approve/deny check the playlist owner beyond `requireFlowAccess` is UNCONFIRMED (`reviewBlockedJob`).
- Already allow-listed (D81/D82/D199): `status`, `jobs`, `jobs/:playlistId`, and Retry
  `POST shared-playlists/:id/tracks/:jobId/research` (which also serves flows). Aurral job states: `pending`,
  `downloading`, `done`, `failed`, `saved`, `blocked`, `cancelled`, `cancel_requested`.

**Navidrome (github.com/navidrome/navidrome, master).** `GetPlaylists` (Subsonic) calls `playlists.GetAll`; the repository's
`userFilter` (`persistence/playlist_repository.go` ~85) returns **everything for an admin**, otherwise only `public` ones
plus the caller's own. The Subsonic `username` parameter is ignored. So "all" can only ever mean "every playlist this
account is allowed to see": for an ordinary user, own + others' public ones; for an admin, also others' private ones. The
list `getPlaylists` already gives (with `owner`, `public`) is that set; Magpie's All/Yours (D179) filters it on the phone.
No new route and no way to see another user's private playlist as a non-admin.

**slskd (github.com/slskd/slskd, master, `ServerController.cs`).** `GET /api/v0/server` (`[Authorize(Policy=Any)]`) returns
the server state (`ServerState`: `isConnected`, `isLoggedIn`, `isTransitioning`, `state` flags such as `Connected, LoggedIn`);
`PUT /api/v0/server` (no body, `ReadWriteOrAdministrator`) connects (it starts or restarts the `ConnectionWatchdog`, which
then reconnects by itself), `DELETE /api/v0/server` disconnects (never called). Magpie already needs a read-write key
for D192's deletes. Exact field names and the PUT's status code (202/200) are to be pinned from the dev stack's slskd
(the repo's `dev/` stack has none for slskd: UNCONFIRMED, so the first RED test uses the real JSON sample captured from
slskd's own `State.cs` shape, then the owner confirms on his server read-only).

**iOS background limits.** A suspended app cannot poll. Options: while the app runs or audio plays (the existing 30 s
runner tick, R16) and a `BGAppRefreshTask` (system-chosen, at best every ~15 min, ~30 s of run time, not guaranteed;
`RequestsBackgroundRefresh` is the pattern). A "bounded time" therefore counts in checks the app actually made (default:
three failed checks across at least 10 minutes), never a timer that could fire without a check. Notification: local only
(`UNUserNotificationCenter`, already used by `ReadyNotifier`); asked for at the moment the toggle is switched on (not at
launch), with the system prompt; if denied, an in-app banner on Home and the page says so ("Notifications are off, so
Magpie can only tell you inside the app."). No push server (privacy: nothing leaves the phone).

`SongsListView.swift`, `PagedLetterList.swift`; `LetterIndexBar`, `LetterIndex` (`Search/LetterIndex.swift`, `sections` already

### F. CarPlay lists: everything, within Apple's limits (item 8) — **M** — D230–D233

### G. CarPlay Now Playing next/previous (item 11) — **S–M** (find first) — D234–D236

- **Wiring:** CarPlay Now Playing's skip buttons are the system's, driven by `MPRemoteCommandCenter.nextTrackCommand` /

- **Hypotheses to verify, each with a RED test, in the order of likelihood:**
  1. **A stale preview swallows the command.** `previewTakes(.nextTrack, preview)` returns true when a preview is "loading,

     nothing happens. Test: queue of 3 with the second unplayable; expect next to skip to the third or say why.

     builds the bridge; a CarPlay-only launch (no phone scene) or a re-created bridge double-registers or never registers.
     Test: scene connect/disconnect/connect leaves exactly one target per command.
  5. **Handler hop.** `commandHandler` returns `.success` before `next()` runs when off-main (`Task { @MainActor }`), so a
     failure isn't reported; the system may then not show progress. Lowest likelihood.
